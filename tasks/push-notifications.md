# Web Push notifications

Closed-app delivery via Web Push + home-screen badge updates.
Server-built generic notification body (`"New message from
{handle}"`), no decrypt-in-SW. The service worker stays free of
Megolm keys and the WASM crypto module.

Specs:
[ADR-0015](../docs/decisions/adr-0015-web-push.md),
[mvp-v0.1.md#push-notifications](../docs/specs/mvp-v0.1.md#push-notifications),
[mvp-v0.1.md#users/{user_id}/devices/{device_id}.json](../docs/specs/mvp-v0.1.md#usersuser_iddevicesdevice_idjson),
[ops.md#server-runtime-env-vars](../docs/ops.md#server-runtime-env-vars).

## Current state

- Service worker is generated by
  [vite-plugin-pwa](../web/vite.config.ts) with Workbox. Strategy:
  `registerType: 'prompt'`. No custom SW source file exists; the
  SW only handles precaching today.
- `POST /v1/send` ([handlers.go:339](../server/handlers.go#L339))
  ends with `hub.Notify(toUser, "new_message")` (SSE only). No
  Web Push fan-out.
- [server/config.go](../server/config.go) has no VAPID
  configuration.
- [server/handlers.go](../server/handlers.go) `register` and
  device handlers don't write `push_subscription` to device.json;
  the field doesn't exist yet.
- [server/store.go](../server/store.go) `Device` struct has
  `device_id`, `device_label`, `created_at` only.
- No client-side notification permission flow. No settings toggle.
- iOS install flow is in [ios-install-hint](ios-install-hint.md)
  (still in queue); this task depends on it for the iOS path but
  ships independently — iOS users just don't get notifications
  until both have landed.

## Architecture constraints

- `lib/` does the network work; the service worker handles push
  events. The SW is built separately by VitePWA — switching to
  `injectManifest` strategy lets us own a custom SW source while
  Workbox still handles precaching ([vite-plugin-pwa docs](https://vite-pwa-org.netlify.app/guide/inject-manifest)).
- The SW **does not** import WASM, decrypt anything, or touch
  Megolm session keys. Generic-body notifications mean the SW
  only needs `showNotification`, `clients.matchAll`, and an
  IDB read/write for the badge counter.
- Push send is best-effort, off the `/v1/send` critical path. A
  failing push must never produce a non-200 response from
  `/v1/send`.

Staging and production carry distinct pairs; documented in

### 2. New endpoint: `GET /v1/push/vapid-public-key`

Unauthenticated. Returns `{ "public_key": "..." }` with the
base64url-encoded VAPID public key. ~10 lines in
[handlers.go](../server/handlers.go), one route in
[routes.go](../server/routes.go).

Set `Cache-Control: public, max-age=86400` — the VAPID key
changes only on environment recreation (key rotation), so a
24-hour client/CDN cache is safe and saves one request per
fresh page load. Clients also persist the key in `localStorage`
on first fetch; the cache header is belt-and-braces for
proxies and the browser HTTP cache.

The endpoint exists so the client can subscribe without
hardcoding the key.

### 3. Device record gains `push_subscription`

[server/store.go](../server/store.go) `Device` struct:

```go
type Device struct {
    DeviceID         string             `json:"device_id"`
    DeviceLabel      string             `json:"device_label"`
    CreatedAt        string             `json:"created_at"`
    PushSubscription *PushSubscription  `json:"push_subscription,omitempty"`
}

type PushSubscription struct {
    Endpoint  string `json:"endpoint"`
    P256DH    string `json:"p256dh"`
    Auth      string `json:"auth"`
    CreatedAt string `json:"created_at"`
}
```

`omitempty` keeps the wire shape identical for devices without
push enabled.

### 4. New endpoints: `PUT` / `DELETE /v1/devices/{device_id}/push`

[handlers.go](../server/handlers.go) gains two handlers, wired
in [routes.go](../server/routes.go) with `auth(...)`.

Authorization: caller's `user_id` (from token) owns
`users/{uid}/devices/{did}.json`. Verify `device_id` in the URL
matches the token's `device_id` — a user can only manage their
own device's subscription, not their sibling devices'. (Rationale:
push subscription is per-browser; one device can't subscribe on
behalf of another.)

`PUT` flow:

```go
func handleDevicePushPut(store Store) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        uid := userIDFrom(r.Context())
        tokenDID := deviceIDFrom(r.Context())
        urlDID := r.PathValue("device_id")
        if urlDID != tokenDID {
            writeError(w, errForbidden)
            return
        }
        var sub PushSubscription
        if err := json.NewDecoder(r.Body).Decode(&sub); err != nil {
            writeError(w, errBadRequest)
            return
        }
        if sub.Endpoint == "" || sub.P256DH == "" || sub.Auth == "" {
            writeError(w, errBadRequest)
            return
        }
        sub.CreatedAt = time.Now().UTC().Format(time.RFC3339)

        dev, err := getDevice(r.Context(), store, uid, urlDID)
        if err != nil { /* ... */ }
        dev.PushSubscription = &sub
        if err := putDevice(r.Context(), store, uid, dev); err != nil {
            internalError(w, "Failed to update device")
            return
        }
        w.WriteHeader(http.StatusOK)
    }
}
```

`DELETE` is the same shape but sets `PushSubscription = nil` and
writes back.

### 5. Push-send hook in `/v1/send`

[handlers.go:339](../server/handlers.go#L339) `handleSend`,
after the existing `hub.Notify` loop:

```go
go fanOutPush(r.Context(), store, cfg, recipients, fromUser, fromDevice)
```

`fanOutPush` (new function, in `server/push.go`):

1. Resolves the sender's handle once from `profile.json` (carries
   `handle` directly; no `handles/` round-trip).
2. For each recipient `uid`:
   - List `users/{uid}/devices/`.
   - For each device record with a `push_subscription`:
     - **Skip the originating device.** If `uid == fromUser` and
       `device_id == fromDevice`, this is the sender's own
       send-acknowledgement device — it doesn't want a
       notification for its own message. Sibling devices on the
       same account still get the push (multi-device user
       sending from phone should still badge the laptop).
     - Build the payload `{title, body, url}` (title varies for
       Saved Messages vs. regular DM).
     - POST via `github.com/SherClockHolmes/webpush-go`. Set TTL
       to 24h (recipients offline longer than that probably want
       to learn about the message on next open, not from a stale
       push).
3. On `410 Gone` from the push service, mutate the device record
   to clear `PushSubscription` and `PutObject` it back. This
   read-modify-write is racy against a concurrent
   `PUT /v1/devices/{did}/push` from the same device — see
   [ADR-0015 — Consequences](../docs/decisions/adr-0015-web-push.md#consequences)
   for the accepted failure mode.
4. On other errors, log and continue. Never returns an error to
   the caller — the goroutine is fire-and-forget.

The function takes a `context.Context` but uses `context.WithoutCancel`
(or copies the deadline-free context) so a fast `/v1/send`
response doesn't cancel the in-flight push send.

### 8. SW: push handler

```ts
declare const self: ServiceWorkerGlobalScope;

import { precacheAndRoute } from 'workbox-precaching';
precacheAndRoute(self.__WB_MANIFEST);

self.addEventListener('push', (event) => {
    event.waitUntil(handlePush(event));
});

async function handlePush(event: PushEvent) {
    if (!event.data) return;
    const data = event.data.json() as {
        title: string;
        body: string;
        url: string;
    };

    const visible = await self.clients.matchAll({
        type: 'window',
        visibilityState: 'visible',
    });
    if (visible.length > 0) return; // app open, SSE handles it

    await self.registration.showNotification(data.title, {
        body: data.body,
        tag:  data.url,             // collapse per-conversation
        icon: '/icons/icon-192.png',
        badge: '/icons/badge-72.png',
        data: { url: data.url },
    });

    await bumpBadge();
}

async function bumpBadge() {
    const next = (await readBadgeCount()) + 1;
    await writeBadgeCount(next);
    if ('setAppBadge' in navigator) {
        await navigator.setAppBadge(next);
    }
}
```

`readBadgeCount` / `writeBadgeCount` are IDB helpers in a new
`web/src/lib/sw-badge.ts` (importable from both SW and main app
since IDB works in both contexts).

### 9. SW: notificationclick handler

```ts
self.addEventListener('notificationclick', (event) => {
    event.notification.close();
    const url = event.notification.data?.url ?? '/';
    event.waitUntil((async () => {
        const allClients = await self.clients.matchAll({
            type: 'window',
            includeUncontrolled: true,
        });
        if (allClients.length > 0) {
            // Focus any existing window, then ask the app to navigate.
            // This handles the "user is on /@bob and clicks a
            // /@carol notification" case correctly — without the
            // postMessage, focus() alone leaves the tab on /@bob.
            const client = allClients[0];
            await client.focus();
            client.postMessage({ type: 'navigate', url });
        } else {
            // No existing window — open a fresh one at the target URL.
            await self.clients.openWindow(url);
        }
    })());
});
```

The main app listens for the `navigate` message and routes via
React Router (one `useEffect` in a top-level component such as
[routes/app.tsx](../web/src/routes/app.tsx)):

```ts
useEffect(() => {
    if (!('serviceWorker' in navigator)) return;
    const handler = (event: MessageEvent) => {
        if (event.data?.type === 'navigate' && typeof event.data.url === 'string') {
            navigate(event.data.url);
        }
    };
    navigator.serviceWorker.addEventListener('message', handler);
    return () => navigator.serviceWorker.removeEventListener('message', handler);
}, [navigate]);
```

Single PWA window stays single; chat switches happen via the
existing router, not via a fresh tab.

### 10. SW: pushsubscriptionchange handler

```ts
self.addEventListener('pushsubscriptionchange', (event) => {
    event.waitUntil((async () => {
        const sub = await self.registration.pushManager.subscribe({
            userVisibleOnly: true,
            applicationServerKey: await fetchVAPIDKey(),
        });
        await postSubscriptionToServer(sub);
    })());
});
```

Without this, subscriptions silently expire after a browser-
specific window (weeks to months) and notifications stop without
an obvious cause.

### 11. Badge clear on app focus

Main app, in [routes/app.tsx](../web/src/routes/app.tsx) or a
new top-level hook `useBadgeClear`:

```ts
useEffect(() => {
    const onVisible = async () => {
        if (document.visibilityState === 'visible') {
            await writeBadgeCount(0);
            if ('clearAppBadge' in navigator) {
                await navigator.clearAppBadge();
            }
        }
    };
    document.addEventListener('visibilitychange', onVisible);
    onVisible(); // also clear on initial mount
    return () => document.removeEventListener('visibilitychange', onVisible);
}, []);
```

### 13. Settings UI: notifications toggle

New component
[web/src/components/NotificationSettings.tsx](../web/src/components/NotificationSettings.tsx),
hosted by the existing [ProfileSettings](../web/src/components/ProfileSettings.tsx)
layout. Behaviour:

- If `'serviceWorker' in navigator && 'PushManager' in window` →
  toggle is interactive.
  - If `Notification.permission === 'granted'` and a subscription
    exists → toggle shows as ON; flipping it OFF unsubscribes
    and DELETEs server-side.
  - If permission is `'default'` or no subscription → toggle is
    OFF; flipping it ON requests permission, subscribes via SW,
    PUTs to server. If permission is denied, surface an
    explanatory line ("Enable notifications in your browser
    settings to use this feature").
- If the platform is iOS Safari but the app is **not** installed
  (`!window.matchMedia('(display-mode: standalone)').matches`),
  toggle is disabled with copy: *"Install atmin to your home
  screen to enable notifications on iOS. [Show me how]"* — the
  link triggers the [ios-install-hint](ios-install-hint.md)
  flow.
- If Push API is unavailable entirely → toggle is hidden.

A new hook
[web/src/hooks/useNotificationSubscription.ts](../web/src/hooks/useNotificationSubscription.ts)
owns the subscribe/unsubscribe orchestration.

## Out of scope

- **Decrypt-in-SW notification bodies.** Explicit ADR-0015 call.
  Would land as its own follow-up if ever requested.
- **Cross-device badge sync.** Each device tracks its count
  locally; multi-device users see slight staleness on
  unopened devices; self-corrects on focus.
- **Notification actions (reply / mark read inline).** Web
  Notifications support `actions` — out of scope; would need
  inline-decrypt or a roundtrip that the generic-body design
  doesn't have.
- **Per-conversation mute.** Settings toggle is global. Per-chat
  muting is its own UX feature.
- **Scheduled or quiet-hours notifications.** Defer.
- **Server-side delivery dedup.** Push fires to every subscribed
  device every time; client SW skips display when visible.

## Verify

`make fmt lint test` clean.

**Go tests (server):**

- `handlers_test.go`:
  - `GET /v1/push/vapid-public-key` returns the configured
    public key, unauthenticated. Returns the same value
    twice (idempotent, cacheable).
  - `PUT /v1/devices/{did}/push`: authenticated caller's own
    device — 200, `push_subscription` round-trips on
    `device.json`. Missing or empty `endpoint`/`p256dh`/`auth`
    → `400 bad_request`. Caller's *sibling* device (different
    `device_id`) → `403 forbidden`.
  - `DELETE /v1/devices/{did}/push`: clears the field; round-trip
    confirms.
  - Authorization regression: caller A cannot PUT a subscription
    on caller B's device.
- New `server/push_test.go`:
  - `fanOutPush` sends one push per device-with-subscription.
    With a mocked push transport: assert the right number of
    invocations and the payload shape (`title`, `body`, `url`).
  - Saved Messages case (`from_user == to_user`) uses
    `"Saved Messages"` title, no handle leak.
  - **Originating-device exclusion**: sender has two devices
    (A and B), both with subscriptions. Message sent from
    device A. Assert exactly one push fires — to device B.
    Device A (the originator) does **not** receive a push for
    its own send.
  - **Empty-recipient cases**: recipient with zero devices →
    zero pushes, no errors. Recipient with devices but none
    subscribed → zero pushes, no errors. Both are no-op fast
    paths.
  - `410 Gone` from the push transport causes
    `push_subscription` to be cleared on that device record.
  - Other errors (timeout, 5xx) are logged but do not clear
    the subscription.
  - **Device-record race demonstration** (regression
    documentation, not a fix): start a `fanOutPush` whose
    push transport returns `410 Gone` after a short delay.
    During that delay, perform `PUT /v1/devices/{did}/push`
    with a fresh subscription. Assert that the
    `fanOutPush` clear-on-410 wins the last-write-wins race
    — the fresh subscription is clobbered. Documents the
    failure mode pinned in
    [ADR-0015](../docs/decisions/adr-0015-web-push.md#consequences);
    the test exists so we *notice* if a future change either
    fixes the race (test would fail and prompt updating the
    ADR) or worsens it.
  - `fanOutPush` does not block `/v1/send` — handler-level test
    with a 5-second sleep injected into the mock transport;
    `/v1/send` returns 200 within 100 ms.

**Playwright e2e (`web/e2e/push-notifications.spec.ts`):**

Playwright supports stubbing the push service via
`page.context().grantPermissions(['notifications'])` and
intercepting `pushManager.subscribe`. Realistic e2e for actual
push delivery isn't possible without a real push service in CI;
the spec covers the subscribe/unsubscribe flow and the SW's
visible-state branch.

1. Alice registers and grants notification permission via the
   settings toggle. PUT to `/v1/devices/{did}/push` observed in
   the network log.
2. Bob registers, opens a chat with Alice, sends a message.
   With Alice's tab visible: no notification is rendered (SW
   skip-on-visible).
3. Alice's tab is backgrounded (set `visibilityState` via
   `page.evaluate`). Bob sends another message. The SW's `push`
   event handler is triggered via a manually-fired event
   (Playwright + `chrome.serviceWorker.dispatchEvent`-style
   helper); `showNotification` is called with the expected
   payload.
4. The badge counter (IDB) is bumped. Alice focuses the tab;
   the counter clears.
5. Alice toggles notifications OFF; DELETE to `/v1/devices/{did}/push`
   observed; subscription gone from device record (verify via
   another GET).

**Manual:**

- Real phone (Android Chrome): register, install to home screen,
