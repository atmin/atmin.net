# v0.3 Spec

Status: draft — the deferred bucket from the [v0.2](v0.2.md) rescope. v0.2
shipped the UI revamp; v0.3 returns to capability, with **group chats as the
headline.** Builds on the frozen [v0.1](mvp-v0.1.md) baseline; everything is
additive **except** the multipart-media `attachments[]` break (below), a
deliberate clean break paid once.

Scope is firming up — sections marked _(sketch)_ are provisional. New decisions
land as ADRs; this spec collects the protocol/API surface as it solidifies.

## Group chats _(sketch — the v0.3 headline; needs an ADR)_

The encryption primitive already fits: Megolm is a group ratchet, and 1:1 today
is just a group of two. A group extends the same shape — encrypt once with an
outbound Megolm session, wrap the session key per member via ECIES, fan out one
inbox envelope per member (`POST /v1/send` already writes to multiple
recipients). The hard parts are **membership** and **rekeying**, not message
encryption.

**Group identity & state.** A group is a `group_id` (ULID) with a state object
holding membership + metadata (name, avatar, `members[]`). Open question — where
it lives and who is authoritative:

- a server-held membership list (server learns the social graph but not
  content), versus
- a client-signed, encrypted group-state blob that members replicate (server
  stays content-agnostic, consistent with the v0.1 threat model).

The second fits the existing "server stores opaque blobs" stance better but needs
a conflict-resolution story for concurrent membership edits (no server
transactions — the same constraint the per-handle mutex works around).

**Sending.** Sender encrypts with its current outbound Megolm session, uploads
the session key wrapped per member (ECIES to each member's sharing key, exactly
as today), and writes one envelope per member inbox carrying `group_id`.
Materialization groups by `group_id` instead of by sender pair.

**Membership changes & rekey.**

- _Add_ — existing members share the current session key with the joiner,
  forward-only unless we deliberately share history (history-visibility is a
  decision; forward-only is simpler and safer).
- _Remove_ — the group rotates to a fresh Megolm session so the removed member
  cannot read future messages (backward secrecy). Reuses the "start a new
  outbound session" mechanism rotation already triggers.

**Addressing — chat URL fragments ([ADR-0024](../decisions/adr-0024-chat-url-fragments.md)).**
A room is addressed `atmin.net/#{chat-id}` — `@` for people (path, public,
server-resolvable), `#` for rooms (fragment, client-only) so the room id never
reaches the relay's request line, access logs, or `Referer`, and an invite secret
rides the same fragment (a capability URL). ADR-0024 fixes only *addressing*; it
stays Draft and is **accepted together with** the group-chats ADR that ratifies
the membership/state model it serves.

**Open / deferred.** Membership authority (flat vs admin roles); ordering of
concurrent membership edits; fan-out cost at larger N (per-member key share +
per-member inbox write — fine for small groups, needs batching/limits otherwise);
group invites/discovery (extend handle-based invite, or invite links); metadata
privacy (encrypt group name/avatar like `contacts.json`).

This is the largest single feature in v0.3 and crosses the trust boundary +
storage layout, so it gets its own ADR before implementation and likely splits
into several tasks (state model, send/fan-out, membership + rekey, UI).

## Multipart media — Phase 2 albums _([ADR-0022](../decisions/adr-0022-multipart-media.md))_

A media message carries an **ordered list of attachments** (an album), each
optionally captioned and previewed, replacing v0.1's single `file`. This is the
one place the protocol evolves a v0.1 wire format — a deliberate clean break (no
back-compat mirror), safe because the inner payload is parsed at render time, so
an un-upgraded client stores the message and re-renders it correctly after update
([ADR-0022](../decisions/adr-0022-multipart-media.md) §2). The single-image
quality fields it generalizes already shipped in
[v0.2](v0.2.md#media--single-image-quality-suite-phase-1-shipped).

### Payload shape

The `type:'media'` inner plaintext gains `attachments[]` and drops `file`:

```json
{
  "type": "media",
  "body": "vacation pics!",
  "attachments": [
    {
      "url": "media/<user_id>/<ulid>",
      "key": "<base64 AES-256-GCM key>",
      "iv": "<base64 12-byte IV>",
      "name": "beach.jpg",
      "size": 318472,
      "mime": "image/jpeg",
      "width": 2048,
      "height": 1536,
      "caption": "sunset, night one",
      "optimized": true,
      "preview": {
        "url": "media/<user_id>/<ulid>",
        "key": "<base64 AES-256-GCM key>",
        "iv": "<base64 12-byte IV>",
        "width": 320,
        "height": 240
      }
    }
  ]
}
```

| Field | Notes |
|---|---|
| `body` | Optional message-level text (distinct from per-attachment `caption`). |
| `attachments[]` | Ordered, 1–10 entries. |
| `url` / `key` / `iv` | Per-object, exactly as v0.1's `file` — each object independently keyed. |
| `name` / `size` | Filename + ciphertext-adjacent plaintext size; used by the non-image chip without a fetch. |
| `mime` | Layout hint only; render still sniffs decrypted bytes before treating as image. |
| `width` / `height` | Source dimensions, for zero-layout-shift sizing. |
| `caption` | Optional per-attachment description. |
| `optimized` | `false` ⇒ the true original was sent. |
| `preview` | Omitted below the preview threshold; otherwise a separate encrypted object + its dimensions. |

Legacy single-`file` messages (v0.1) remain readable **indefinitely** — new
clients dual-read both shapes. An un-upgraded client drops a new `attachments`
message (renders nothing) until it updates; no data is lost (it persists in S3
and locally) and it self-heals on update
([ADR-0022](../decisions/adr-0022-multipart-media.md) §2).

### Limits

- **≤ 10 attachments** per message.
- **25 MB ciphertext cap per object**, unchanged from v0.1
  [Media](mvp-v0.1.md#media) (per object, not per message).
- Every object — each full **and** each preview — is its own
  `media/{uid}/{ulid}` and counts against the per-user media quota and the
  1000-blob cap.

### Composer & amendments (delta)

- A **multi-select composer** generalizes the v0.2 single-item compose tray:
  several staged attachments with per-image captions, rendered as a grid.
- **`delete`** sweeps the message's **full object set** (every attachment + every
  preview), not a single blob; the recipient drops all locally cached decrypted
  blobs for the message.
- **`edit`** edits the message-level `body` only; per-attachment captions are
  immutable in this round.

## History export / import _(sketch — export likely, import open)_

**Export (likely).** Entirely client-side: the device already holds full
decrypted history in IndexedDB, so export is read → serialize → download, with no
server or new endpoint.

- _Format_ — a documented JSON archive: conversations and messages (plaintext
  body, timestamps, sender handle, `msg_id`, amendment state), with media either
  referenced by `media/{uid}/{ulid}` or bundled (e.g. a zip alongside the JSON).
  A stable, documented schema is the main deliverable so the file is useful to
  other tools.
- _Privacy_ — export deliberately crosses the E2E boundary (plaintext leaves the
  app); that is a deliberate choice, surfaced with a clear warning. An optional
  passphrase-encrypted export is a possible add-on.

**Import (open, lower certainty).** Backup-key + key-chain restore already
rebuilds history on a new device, so import is not for the normal multi-device
case — its real uses are migrating from another app or restoring an export after
key loss. Open issues:

- Imported messages never went through Megolm/inbox, so they cannot be verified —
  they would be **local-only**, display-marked "imported," and never re-sent or
  re-encrypted.
- Mapping a foreign sender onto a handle/contact is fuzzy.
- Whether import is in v0.3 at all, or export ships alone.

No server/protocol surface for export; import (if it lands) is also client-only.
No ADR unless an encrypted-export format introduces a new crypto decision.

## Extended theming _(sketch)_

Broaden beyond the current light/dark toggle (additional themes / accent
options), built on the existing `index.css` token set so both modes keep working.
Client-only, no protocol surface.

## Not yet scoped

Carried from the [vision roadmap](../vision.md#milestones); no design yet, each
needs its own ADR before it enters this spec:

- Opt-in discovery (phone or other identifier).
- Better abuse controls — rate limiting (in-process `rocket-governor`, deferred
  until abuse appears) and captcha (only if PoW proves insufficient; EU-based or
  self-hosted), beyond the v0.2 registration PoW + reserved list.
- Optional realtime hints beyond best-effort SSE.
